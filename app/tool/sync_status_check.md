# #78 목록 새로고침·동기화 상태 확인

## 구현 범위
- `FirebaseTodoStore.watchAll()`은 `includeMetadataChanges: true`로 문서 내용과 `hasPendingWrites` 변경을 전달한다.
- `FirestoreTodoRepository`는 표시할 목록과 대기 문서 수를 따로 전달한다. 삭제 문서는 숨기지만 삭제 전송 대기는 센다.
- `TodoController`는 구독 결과로 목록·완료 여부·배지를 갱신한다. 계정 전환이나 화면 종료 시 구독을 해제한다.
- 당겨서 새로고침하면 `Source.server`를 요청한다. 서버 조회 실패는 안내하고 기존 목록을 보존한다.
- 빈 목록, 필터 결과 없음, 항목이 적은 목록에서도 새로고침할 수 있다. 사분면은 실시간 변경을 함께 반영한다.
- 기존 오류 카드와 자동 재시도를 유지한다. 오프라인에서는 예약된 목록 재시도를 취소한다.

## 연결 감지
- 새 패키지 없이 Dart `HttpClient`로 `https://firestore.googleapis.com/`의 HTTPS 응답을 확인한다. 인증 정보나 할 일 데이터는 보내지 않는다.
- 연결 확인은 최대 3초, 확인 완료 후 다음 검사까지 3초다. 연결이 끊긴 경우 배너가 표시되기까지 약 6초가 걸릴 수 있다.
- HTTP 5xx 또는 연결 실패는 사용할 수 없는 연결로 처리한다. 이는 인터넷 도달 여부 확인이며 Firebase 인증·보안 규칙 성공을 보장하지 않는다.
- 캐시에서 읽었다는 이유만으로 오프라인이라고 판단하지 않는다. 정상 연결에서도 초기 스냅샷은 캐시에서 올 수 있기 때문이다.
- 앱이 백그라운드로 가면 주기 검사를 중지하고, 복귀하면 다시 확인한다.
- 연결 복구 시 배너를 숨기고 서버 새로고침을 요청한다. 실제 전송 완료 판정은 HTTPS 확인이 아니라 Firestore의 `hasPendingWrites`를 사용한다.

2. A에서 제목 수정·완료 전환·삭제를 수행하고 B의 목록에도 반영되는지 확인한다.
3. B에서 목록을 아래로 당겨 새로고침한다. 빈 목록과 필터 결과 없음에서도 동작하는지 확인한다.
4. A의 Wi-Fi와 모바일 데이터를 모두 끈다. 약 6초 안에 오프라인 배너가 보이는지 확인한다.
5. A에서 새 항목을 작성한다. 목록에 남고 `동기화 대기 1`이 보이는지 확인한다.
6. A의 연결을 복구한다. 배너가 숨겨지고, 수동 새로고침 없이 대기 배지가 완료로 바뀌며 B에도 새 항목이 표시되는지 확인한다.
7. 오프라인에서 마지막 항목을 삭제해도 전송 전까지 대기 배지가 남는지 확인한다.
8. 로그아웃·다른 계정 전환 후 이전 계정의 변경이 목록에 나타나지 않는지 확인한다.

네트워크·Firebase 응답에 따라 실제 반영 시간이 달라질 수 있으므로 복구 후 10초 내 반영 여부도 실기기에서 측정한다. iOS 실행은 Mac에서 별도 확인한다.
